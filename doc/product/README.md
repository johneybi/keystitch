# KeyStitch 제품화 기준선

정리일: **2026-11-11**. 이 문서는 현재 저장소 이름인 KeyStitch를 사용한다.
브랜드·사업 모델·최종 지원 OS를 확정한 문서는 아니다.

지금까지 확보한 핵심 성과는 **Windows에서 전달한 한영 전환을 Mac의 기존
설정으로 처리하고, 전환 직후 후속 키의 순서를 보존했을 때 실제 사용성이
개선된 것**이다. 이를 재현 가능한 설치·설정·검증 체계로 묶는 것이 다음 목표다.

이 문서를 제품 작업의 진입점으로 사용한다. 날짜가 붙은 기존 문서는 당시의
실험·검증 기록으로 보존하며, 과거 문서의 “미설치”, “성공”, “현재 버전”을
오늘의 제품 상태로 그대로 해석하지 않는다.

2026-11-17 UI 작업: [Figma와 독립 QML 미리보기](../../tools/ui-preview/README.md).
메인 화면·키보드 설정·메뉴바를 공통 디자인으로 관리하고 키보드 설정부터
구현했다. 현재 입력 엔진·설치 앱과 연결하지 않은 개발용 화면이다.
사용자는 B 방식이 이후 실사용에서도 잘 작동했다고 추가로 보고했다.
이 피드백과 전체 앱·OS 조합의 정식 검증은 구분한다.

2026-11-18 배포 제품 개발: [설정·엔진 경계와 검증](desktop-foundation.md).
B 선택을 저장하고 명시적 엔진 인수로 전달하는 경로를 구현했다. 로컬 전체
unit suite 301개를 통과했으며 설치 앱은 그대로 유지했다. 아래 11/11의
환경변수 의존·SecureUtils 실패 기록은 당시 기준이며 새 소스에서는 개선됐다.
첫 기반 코드 `166c4353`은 원격 Mac 301개·Windows 236개 unit tests와 각 플랫폼의
패키지 정책 5개도 통과했다. 실행 링크와 남은 출시 조건은 위 문서에 기록했다.

같은 날 `ade651a1`에서 **Mac 앱 ZIP·Windows 설치 EXE의 CI 생성**도 확인했다.
실행 파일의 clean revision/build ID와 최종 해시를 기록한다. Mac 304개·Windows
239개 unit tests, 각 OS의 패키지/metadata 15개 검사가 통과했다. 산출물·실행
링크는 [배포 기반 문서](desktop-foundation.md)에 있다. 현재 앱에는 설치하지
않았으며, 서명·설치 수용·실제 입력 검증을 마친 출시 버전은 아니다.

## 1. 만들려는 제품

**키보드와 마우스 한 세트로 Windows와 Mac을 오가면서, 한영 전환·단축키·
마우스 버튼을 각 운영체제에서 익숙하게 사용하는 입력 공유 제품.**

초기 품질 검증의 중심은 Windows 키보드·마우스 → Mac이다. Mac → Windows는
별도의 실제 제품 검증을 통과한 범위만 지원으로 표시한다. Linux 등 upstream의
지원 범위를 KeyStitch의 검증 범위로 자동 승계하지 않는다.

제품 설계 원칙:

- 사용자가 Mac에서 쓰던 한영 전환 설정과 내장 키보드 사용을 유지한다.
- 구름 입력기는 선택적 호환성 대상이다. 기본 검증은 Apple 한국어와 ABC로 한다.
- Karabiner, Virtual HID, SSH, Codex를 최종 사용자 필수 구성으로 삼지 않는다.
- 설치·재실행·업데이트 후에도 사용자가 선택한 동작이 유지되어야 한다.
- 메뉴 표시, 요청 전송, 입력 소스 선택, 실제 문자열 입력을 구분해서 검증한다.
- 화면 이탈·연결 종료 시 눌린 키와 버튼을 정리하고 오래된 입력을 재전송하지 않는다.
- 지원하지 못하는 설정은 진단한다. 사용자 설정을 조용히 바꾸거나 다른 전환
  방식으로 자동 우회하는 것으로 성공을 만들지 않는다.

이는 제품 목표다. 아래 표의 현재 검증 수준과 구분한다.

## 3. 한영 전환에서 얻은 결론

### 진행 과정

| 단계 | 목적·결과 | 기준 커밋/기록 |
| --- | --- | --- |
| 구름 사용과 선호값 정리 | 기존 입력 불안정의 회피·선택 정책 개선. 구름이 필수이거나 원인이라는 증거는 아님 | `ad72bf9f` |

| 양방향 복원·진단 | 소스 선택 기록과 실제 입력 성공이 다름을 재확인 | `af9c2cb4`, `1560ed9a`, `2127baf1` |

| 실사용 관측 | “굉장히 쾌적해졌다”, 현재 잘 된다는 사용자 피드백을 기록 | `bd7c45f2`, `aa2133a6` |

현재의 개발 후보는 **B + 후속 키 순서 보존**이다. A/B는 실험 명칭이며 최종
제품에서 사용자가 내부 API 이름을 알아야 하는 설정 구조로 굳히지 않는다.

### 현재 입력 경로

```text
Windows 키보드
  → 서버의 대상 화면별 remap / tap·hold 판정
  → 프로토콜 전송
  → Mac의 의미상 F19 요청
  → Mac에 이미 설정된 입력 소스 전환 단축키 전송
  → 선택된 입력 소스의 변경 관찰 + 후속 키 FIFO
  → 순서를 보존한 키 전달
  → 전경 앱의 IME 처리와 실제 문자열
```

Right Alt의 tap은 서버에서 키를 놓을 때 만들어지며, 다른 키와 겹치면 hold로
분류될 수 있다. 내장 키보드의 체감 속도 차이는 원격 전달·tap 판정·클라이언트
처리를 나누어 측정해야 한다. 지금의 관측만으로 각 구간의 기여를 확정하지 않는다.

현재 B 구현의 주요 값:

| 항목 | 구현 | 제품화 시 의미 |
| --- | --- | --- |
| 선택 상태 관찰 | 대기 중 4ms 간격을 목표로 관찰 | 스케줄링 지연과 입력·마우스 트래픽 중 타이머 starvation도 고려 |
| 변경 후 안정 구간 | 20ms | 실험적 guard. 전경 IME 조합 완료 응답이 아님 |
| 대기 제한 | 300ms | 정책상 제한. OS API·메인 스레드 정지까지 제한하지는 못함 |
| FIFO 제한 | 256 keystroke | 초과 시 경고와 함께 원래 입력을 해제. 성공으로 세지 않음 |
| 클릭·스크롤 | 기존 보관 입력을 포인터 이벤트보다 먼저 해제 | 확인되지 않은 해제는 경고로 구분 |
| 화면 이탈·전체 키 해제 | 미전달 입력 폐기, 이미 전달한 down 정리 | 늦게 다른 입력창으로 글자를 보내지 않도록 처리 |

단축키 선호값의 `60` 해석은 비공개 스키마에 대한 호환성 가정이다.
`CopySymbolicHotKeys`의 일치는 단축키 등록 확인이며 해당 동작·IME 완료의 증명이
아니다. 현재 지원되지 않는 단축키 형태도 있으므로 출시 지원 범위가 필요하다.

구현 위치:

- [OSXInputSourceShortcut](../../src/lib/platform/OSXInputSourceShortcut.cpp): 선호값 해석, 등록값 비교, 이벤트 계획.
- [OSXInputSourceTransition](../../src/lib/platform/OSXInputSourceTransition.cpp): 순수 전환 관찰 정책.
- [OSXKeyState](../../src/lib/platform/OSXKeyState.cpp): 실제 경계 호출, FIFO, 타이머, 키 상태·정리.
- [OSXScreen](../../src/lib/platform/OSXScreen.mm): 포인터 이벤트와 입력 순서 연결.
- [KeyRemapper](../../src/lib/server/KeyRemapper.cpp): 서버의 대상 화면별 의미 변환.

## 4. 확인된 검증과 미확인 범위

2026-10-30에 기록된 결과:

- 관련 테스트 **92/92 통과**.
- 전체 **228/230 통과**. 기존 `SecureUtilsTest.FormatSslFingerprintHexWithSeparators`,
  `SecureUtilsTest.CreateFingerprintRandomArt` 실패가 남아 있다.
- FIFO 보관을 고의로 우회하면 회귀 테스트가 실패하는 것도 확인했다.
- 실제 메모리 내 EventQueue로 타이머 연결·취소를 확인했다. 입력 소스 읽기와
  키 전송을 대체한 테스트를 실제 IME 실증으로 세지는 않는다.
- 관측 구간의 B 요청 16회가 모두 `source-stable`로 해제됐다.
  내부 대기는 **40.034–62.407ms, 중앙값 57.089ms**였다.
- 그 구간에서 미확인 해제·요청 거부·연결 오류가 기록되지 않았다.

위 숫자는 입력 소스 관찰과 guard를 포함한 **클라이언트 내부 구간**이다.
키보드에서 브라우저의 문자열이 완성되기까지의 지연이나 장기 성공률이 아니다.
당시 사용 환경은 구름/ABC였고, 새 비교 페이지의 정형 Windows·내장 키보드
각 3회 기록까지 완료된 것으로 해석하지 않는다.

여전히 별도 확인해야 할 것:

- Apple 한국어/ABC 기본 환경 및 선택적 구름 환경의 동일 기준 검증.
- Safari·Chrome·native 필드, 조합 중/조합 없음, 한글↔영문의 실제 문자열.
- 내장 키보드와 원격 키보드의 정량 비교 및 혼용 시 동작.
- 오래 사용하기, 절전·복귀, 네트워크 단절, 큰 클립보드 전송 중 입력.
- Windows 클라이언트의 키·마우스 의미와 실제 브라우저 뒤로/앞으로.

2026-11-11의 이번 정리는 저장된 검증 결과와 설치 파일을 대조한 작업이다.
테스트를 새로 실행하거나 12일 연속 안정적으로 작동했다고 확인한 작업은 아니다.

| Windows 설치본 | 이번 정리에서 새로 확인하지 않음 | 같은 저장소를 pull했다고 설치·실행본이 업데이트되지는 않음 |

현재 Mac 클라이언트 SHA256:

```text
b9ef25734b37c3ddf23af03b76c749a600576357aa260d9e71f53c96305cb8e3
```

추가로 확인된 배포 문제:

1. B는 현재 `INPUTLEAP_MACOS_IME_BACKEND=native-shortcut` 실행 환경으로 선택한다.
   일반 재실행에서는 컴파일 기본값인 A로 돌아간다. **제품 설정으로 저장해야 한다.**
2. 설치 bundle은 `LSMinimumSystemVersion=11.0`이지만 실제 클라이언트의 Mach-O
   최소 OS는 **26.0**이다. 현재 패키지를 macOS 11 지원으로 배포하면 안 된다.
3. 원격 확인 시 IME 개발 브랜치는 아직 없었다. 이번 제품 정리와 개선 소스는
   [이 브랜치](https://github.com/johneybi/keystitch/tree/codex/ime-f19-regression)에서 관리한다.
4. `input-leap-keymap-ci.yml`은 다른 브랜치 이름을 대상으로 하며 Mac 작업은
   unit tests를 끄고 Windows 작업도 제한된 suite만 실행한다. 현재 IME 92개 suite의
   CI 실행 완료를 이번 정리에서 확인한 것은 아니다.
5. 임시 경로가 사라진 worktree 등록도 남아 있다. 이 정리에서는 삭제·prune하지 않았다.

제품 기준선은 “같은 저장소”가 아니라 **서버·클라이언트·GUI의 실제 실행 파일,
빌드 설정, 호환성이 명시된 릴리스 구성**으로 정의해야 한다.

## 6. 코드 구조를 정리할 방향

실증된 B와 회귀 테스트를 기준으로 구조를 정리한다. 권장 책임 분리는 다음과 같다.

| 책임 | 현재 기반 | 정리 방향 — 아직 미구현 |
| --- | --- | --- |
| 공통 입력 의미 | KeyRemapper / KeyRemapConfig | 키·modifier·tap/hold·버튼·입력 소스 전환 의도를 명시 |
| OS 어댑터 | OSXKeyState / MSWindowsKeyState / Screen | 각 OS의 전송·단축키·상태 읽기 경계 유지 |
| 전환 중 입력 순서 | Transition + OSXKeyState 내부 FIFO | 타이머·FIFO·취소를 하나의 수명 관리 단위로 캡슐화 |
| 연결과 전송 | Client / Server / proxy / ClipboardSender | 입력·heartbeat·대용량 전송의 우선순위와 backpressure 명시 |
| 제품 설정·운영 | GUI / 환경변수 / 설치 스크립트 | 저장되는 설정, 시작/종료 책임, 진단·버전 표시를 일원화 |

F19는 현재의 호환 어댑터로 유지할 수 있다. 제품 내부에서 “입력 소스 전환”의
의미를 모델링하되, wire protocol 변경은 버전 협상·구버전 호환 검증과 분리한다.
브랜드 변경만으로 bundle ID와 권한 연결을 무심코 끊지 않는다.

## 7. 테스트를 덜 어렵게 만드는 체계

기존 [record-only runner](https://github.com/johneybi/keystitch/blob/9e2b268e288a05cba783e9024ab6c8296d1db589/tools/pair-test/README.md)를 출발점으로 아래 계층을 구분한다.

| 계층 | 자동화할 대상 | 통과해도 증명하지 못하는 것 |
| --- | --- | --- |
| 순수 정책·회귀 | remap, 전환 상태, timeout, 정리, 순서 | OS·IME·실제 네트워크 입력 |
| record-only codec | 실제 codec, 고정 이벤트, 두 호스트 전송·증거 수집 | 실제 제품의 연결·재접속·키 해제 |
| 실제 제품 + 대체 sink | 실제 Client/Server, handshake, remap, 단절 정리, 클립보드 경합 | 실제 앱의 조합·문자열·브라우저 탐색 |
| OS·IME 수용 테스트 | 별도 입력창, 실제 입력, 두 키보드·양방향 비교 | 장기간·모든 앱의 안정성 |
| 지속 사용 관측 | 절전·재접속·대용량 전송·프로세스·자원 사용 | 검증하지 않은 OS/키보드 조합 |

매 실행에는 공통 run ID와 양쪽의 실제 binary hash/commit/OS/architecture,
설정 식별자, 시나리오·결과를 묶는다. 테스트용 고정 문자열 외에는 입력 내용이나
클립보드 내용을 기본 진단 로그에 남기지 않는다. 호스트별 monotonic 시각만으로
두 컴퓨터 사이의 정확한 지연을 계산하지 않는다.

설치본과 시험용 실행본은 경로·설정·포트를 분리하고 각 실행의 프로세스 소유자를
명확히 한다. 기존 양쪽 Codex 채팅을 활용하는 실행 방식은 개발 편의 기능이다.
SSH 활성화나 채팅 자체가 제품과 테스트 프로토콜의 필수 조건은 아니다.

## 8. 제품화 이정표와 완료 조건

기간 약속 대신 완료 조건으로 진행한다. 아래는 권장 순서이며 완료 표시가 아니다.

| 단계 | 실제 작업 | 다음 단계로 넘어가는 조건 |
| --- | --- | --- |
| M0: 기준선 고정 | 두 코드 계열과 현재 실행본 대조, Windows 설치본 확인, 포함할 변경 선정, release manifest 작성 | 각 파일의 원본·설정·호환 조합을 재현 가능. 로컬/원격/설치본 식별 가능 |
| M1: 일상 실행 완성 | B 선택의 설정 저장·재시작 유지, 일관된 상태·버전 표시, 프로세스 수명·복구, 최소 OS 정정 | 수동 환경변수 없이 같은 동작으로 다시 켜짐. Mac 설정 보존. 정상 종료·이탈 시 입력 정리 |
| M2: 반복 가능한 제품 테스트 | runner와 실제 Client/Server 대체-sink 통합, 양 OS 빌드·CI, 알려진 실패 원인 해결 | 동일 run ID로 재현. 수정된 suite가 실제로 실행됨. SecureUtils 두 실패를 근거 없이 숨기지 않음 |
| M3: 입력 품질 수용 | Apple 한국어/ABC, 선택적 구름, Chrome/Safari/native, 빠른 조합·연속 전환·modifier·추가 버튼 | 실제 문자열·순서·키 해제 검증. 물리 버튼 4/5 전송과 뒤로/앞으로 의미를 각각 검증 |
| M4: 배포 후보 | 일관된 Windows/Mac 패키지, 서명·권한 안내, 인증·암호화·페어링, 설치/업그레이드/복구 | Codex·수동 스크립트 없이 설치·연결. 최소 OS와 실제 의존성 일치. 시험용 암호화 해제 설정 배제 |

각 단계의 수용 시나리오에는 최초 설치/재실행, 한글↔영문, 조합 중/없음,
연속 빠른 입력, 화면 이탈, 끊김/재접속, 절전/복귀, 큰 텍스트·이미지 클립보드,
Windows와 Mac 역할 교환을 포함한다. 지원 범위에 넣지 않은 조합은 미지원/실험으로
표시한다. end-to-end 지연 예산과 장기 관측 시간은 측정 방법과 함께 따로 정한다.

마우스 추가 버튼·클립보드 경합·Windows 클라이언트 검증은 이 제품의 핵심
품질 범위다. 오디오 릴레이와 드라이버 경로 등 확장 기능은 별도 선택 기능으로
관리하고, 최초 입력 공유 제품의 완료 조건과 섞지 않는 것을 권장한다.

## 9. 배포와 사업 모델의 기준

현재 [LICENSE](../../LICENSE)는 GNU GPL v2 본문과 OpenSSL 예외를 포함한다.
GPL은 상업적 판매를 허용하지만, 파생 프로그램의 배포에는 해당 라이선스·
소스 제공 조건을 함께 검토해야 한다.
[GNU FAQ](https://www.gnu.org/licenses/gpl-faq.en.html#DoesTheGPLAllowMoney),
[GPL v2 FAQ](https://www.gnu.org/licenses/old-licenses/gpl-2.0-faq.html).

자체 브랜드·UX·설치·지원·품질 기준을 갖춘 제품으로 발전시킬 수 있다.
기존 저작권 고지·라이선스는 보존하고 Qt/OpenSSL 및 선택적으로 포함할 외부
구성요소의 실제 배포 조건을 목록화한다. 비공개 소스 배포가 사업 요구라면
개발 범위와 라이선스 전략을 먼저 확정해야 한다. 이 문서는 라이선스를 변경하거나
특정 배포 형태의 적법성을 확정하는 문서가 아니다.

## 10. 바로 다음 개발의 범위

먼저 **M0 기준선과 M1의 B 설정 저장**을 묶은 작은 배포 후보를 만드는 것을 권장한다.
사용자가 확인한 B 동작을 회귀 테스트로 고정하고, 설치·재시작·버전 식별을
재현 가능하게 만든다. 그다음 실제 제품을 사용하는 테스트 체계를 연결한다.

큰 정리 작업에서도 실사용 앱을 보존하고 시험 실행본을 분리한다. 서로 다른
계열의 브랜치를 확인 없이 합치거나 오래된 실험을 기본값으로 되돌리지 않는다.
현재 기록과 테스트를 살리면서 책임을 나누는 것이 제품화의 출발점이다.

이 정리 작업 자체는 문서 변경이다. 앱 교체·실행·설정 변경·새로운 실증 테스트·
다른 worktree 정리·제품 브랜치 병합을 수행한 것으로 읽지 않는다.
